# Authoriza

A Next.js application with shadcn/ui, Drizzle ORM and PostgreSQL.

## Adding components

To add components to your app, run the following command:

```bash
pnpm dlx shadcn@latest add button
```

This will place the ui components in the `components` directory.

## Using components

To use the components in your app, import them as follows:

```tsx
import { Button } from "@/components/ui/button"
```

## Database

The app uses [Drizzle ORM](https://orm.drizzle.team) with PostgreSQL through the `pg` driver.

- Schema: `db/schema/` (one file per table, relations in `relations.ts`)
- Client: `db/client.ts` exports `db` (Drizzle) and `pool` (node-postgres)
- Migrations: `db/migrations/` generated by drizzle-kit from `drizzle.config.ts`

### Setup

1. Copy `.env.example` to `.env` and set `DATABASE_URL`.
2. Create the databases named in `.env` and `.env.test`.
3. Apply the migrations to the development database:

```bash
pnpm db:migrate
```

The test database does not need this step: the integration tests run the migrations themselves before the first test.

### How each tool reads the environment

The three entry points do not resolve `.env` files identically, which matters when you add overrides.

| Entry point               | Files read                                                                                                                                  |
| ------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| `next dev` / `next build` | Next's own loader: `.env.development*` or `.env.production*`, then `.env`                                                                   |
| `pnpm db:*` (drizzle-kit) | drizzle-kit preloads `.env` itself before the config runs, and a variable already set always wins, so `.env.local` does **not** override it |
| `pnpm test` (vitest)      | `NODE_ENV` is pinned to `test`, so `@next/env` reads `.env.test`, then `.env`                                                               |

A variable exported in your shell beats every file, in all three. `DATABASE_URL` is validated at import time, so a missing or non-Postgres value fails immediately rather than at the first query. Set it in CI and in any Docker build stage that runs `next build` once a route imports the database client.

### Scripts

| Script               | What it does                                                       |
| -------------------- | ------------------------------------------------------------------ |
| `pnpm db:generate`   | Generate a SQL migration from schema changes                       |
| `pnpm db:migrate`    | Apply pending migrations to the database in `.env`                 |
| `pnpm db:push`       | Push the schema directly without a migration (prototyping only)    |
| `pnpm db:studio`     | Open Drizzle Studio                                                |
| `pnpm test`          | Run all tests (integration tests need the database in `.env.test`) |
| `pnpm test:unit`     | Run everything except the `*.integration.test.ts` suites           |
| `pnpm test:coverage` | Run all tests with coverage (80% thresholds)                       |

Database-backed tests truncate `users`, `profiles` and `sessions`, so `vitest.setup.ts` refuses to start unless the resolved database name ends in `_test`. Note that `pnpm test:unit` is not a no-database run: it only drops the `*.integration.test.ts` files, and the route handler and bootstrap-script suites still need `.env.test` to point at a reachable database.

### Tables

- `users`: `id` (uuid), `email` (unique), `password_hash`, `role` (`admin` or `hr`, default `hr`), `email_verified_at`, `remember_token`, `created_at`, `updated_at`
- `sessions`: `id` (uuid), `user_id` (references `users.id`, cascades), `token_hash` (unique), `expires_at`, `revoked_at`, `last_used_at`, `ip`, `user_agent`
- `profiles`: `id` (uuid), `user_id` (unique, references `users.id`, cascades on delete), `first_name`, `last_name`, `avatar_url`, `created_at`, `updated_at`

Timestamps are `timestamp with time zone`, which PostgreSQL always stores as UTC. The database connection also pins its session zone to UTC, so reading a row and casting it to a date give the same answer on every machine, not the host's local zone.

`users` and `profiles` are one-to-one: the unique constraint on `profiles.user_id` enforces it at the database level, and `db.query.users.findFirst({ with: { profile: true } })` loads both sides.

Two deliberate limits worth knowing before you store real accounts. Email uniqueness is case-sensitive, so `Ada@example.com` and `ada@example.com` are different users; normalise at the boundary or add a `lower(email)` unique index. And `password_hash` is `NOT NULL`, which suits password login but would need a nullable column or a separate credentials table to support OAuth or passkeys.

## Authentication

`POST /api/auth/login` verifies a password and issues a session. The page lives at `/auth/login`, built from the shadcn `login-05` block with a password field added, since that block ships email-only.

The chain follows the domain-driver layout: the form calls a hook, the hook posts to the route handler, and the handler calls the server service, which calls the server repository. There is no client-side service or repository; the hook talks to the endpoint directly.

| Layer             | File                                                     |
| ----------------- | -------------------------------------------------------- |
| Page              | `app/auth/login/page.tsx`                                |
| Form              | `app/auth/login/components/client/LoginForm.tsx`         |
| Hook              | `app/auth/login/hooks/Login.hook.ts`                     |
| Route handler     | `app/api/auth/login/route.ts`                            |
| Server service    | `app/auth/login/server/services/Login.service.ts`        |
| Server repository | `app/auth/login/server/repositories/Login.repository.ts` |

### How a session works

Passwords are hashed with argon2id through `@node-rs/argon2`, whose defaults already match the OWASP parameters. On success the server generates 32 random bytes as the session token, stores only its SHA-256 digest in `sessions`, and returns the token in an httpOnly cookie named `authoriza_session`. Browser JavaScript cannot read it, and a database dump cannot be replayed as a live session. Sessions last `SESSION_TTL_MINUTES` and record the IP and user agent they came from.

### Remember me

Modelled on Laravel's `SessionGuard`. Two cookies, two lifetimes, and a token on the user row.

|                      | Lifetime                                                    | Holds                                         |
| -------------------- | ----------------------------------------------------------- | --------------------------------------------- |
| `authoriza_session`  | `SESSION_TTL_MINUTES` (60, or `null` for never)             | the session token                             |
| `authoriza_remember` | `SESSION_REMEMBER_TTL_MINUTES` (576000, Laravel's 400 days) | `userId\|remember_token\|hmac(password_hash)` |

### Session lifetime

`SESSION_TTL_MINUTES` has two modes, the same two Sanctum offers.

| Value  | Behaviour                                                                             |
| ------ | ------------------------------------------------------------------------------------- |
| `60`   | The session expires after 60 minutes. A remembered device gets a new one on the spot. |
| `null` | The session never expires. Only signing out, or revoking the row, ends it.            |

`null`, `none` and `never` all mean no expiry. Leaving the line out keeps the 60-minute default, and an empty value is an error rather than a third meaning, so a half-deleted line cannot quietly make every session eternal. A never-expiring session stores `NULL` in `sessions.expires_at`, and liveness is `expires_at IS NULL OR expires_at > now()`. Its cookie is given 400 days, the longest any browser will keep one.

Ticking the box does not lengthen the session. It stores a 60-character `remember_token` on the user and issues the second cookie. When the session later expires, the guard redirects to `/api/auth/recall`, which checks the token with a constant-time compare, checks that the HMAC still matches the current password hash, mints a fresh session of the usual length and continues to the page you asked for.

That HMAC is why changing a password signs out every remembered device without touching the token. The route only ever redirects to a path inside the app, so `next` cannot be used as an open redirect.

The token is one per user, exactly as in Laravel, which has a consequence worth knowing: signing out on one device clears it and so forgets every remembered device. Ordinary sessions on other devices keep working until they expire.

The recall lives in a route handler rather than in `proxy.ts` because a Next Server Component cannot set cookies, and Next's own guidance is to avoid middleware unless nothing else works. The cost is one redirect on the first visit after a session expires.

`APP_SECRET` keys that HMAC and must be at least 32 characters. It is the only secret the app needs.

### Security decisions worth knowing

- A wrong password and an unknown email return the identical 401 body. The unknown-email path still runs a real argon2 verification against a dummy hash, so response time does not reveal which addresses are registered.
- Email is trimmed and lowercased before validation, because `users.email` is case-sensitive.
- Login is rate limited per email (5 per 15 minutes) and per IP (20 per 15 minutes), returning 429 with `Retry-After`. The counters live in process memory, so they reset on restart and are not shared between instances. Moving them into Postgres is the upgrade path.
- An unverified email does not block login. The response carries an `emailVerified` boolean instead, because a distinct "please verify" reply would confirm both the address and the password.

### Roles

`users.role` is a PostgreSQL enum, `admin` or `hr`, so an unknown role cannot be written at all. New rows default to `hr`, the lesser privilege. There is no self-registration: an admin provisions accounts, and onboarding happens on another system.

Guard a page with `requireSession()` for "must be signed in" or `requireRole("admin")` for a specific role. Both live in `lib/current-session.ts` and are called inside the page that needs them, rather than once in a proxy, so the check sits beside the data it protects. A signed-in user without the role is refused rather than redirected, since sending them back to login would loop.

### Creating the first account

The database starts empty and nothing can sign in. Bootstrap one account:

```bash
pnpm user:create-first --email you@example.com \
  --first-name Ada --last-name Lovelace --role admin --password 'something-long'
```

The password must be at least 12 characters, stricter than the login form, because this account provisions every other. Be aware that a command line is written to your shell history and is readable by `ps` while the process runs.

The script writes the user and the profile in one transaction and refuses to run once any user exists. Everyone after the first is provisioned by an admin.

### Signing out

`POST /api/auth/logout` stamps `revoked_at` on the current session and clears the cookie. The row is kept rather than deleted, so a sign-out stays in the audit trail, and only the current device is affected. It always answers 200, even without a session, because signing out is not a place to reveal whether a token was real.

## Tooling notes

- ESLint is pinned to `^9`. The scaffold shipped `^10`, but `eslint-config-next` depends on `eslint-plugin-react` 7.37.5, which throws `contextOrFilename.getFilename is not a function` under ESLint 10.
- `pnpm-workspace.yaml` approves four build scripts: `sharp`, `unrs-resolver`, `domain-driver` (its postinstall writes the agent guidance files) and `esbuild` (a transitive dependency of drizzle-kit and vitest). It blocks `msw`.
